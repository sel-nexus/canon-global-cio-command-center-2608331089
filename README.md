# Canon Global CIO Command Center — executive dashboard

This repository currently implements account registration, login, verified profile restoration, logout, Strategic Command, Executive Summary regional comparison, Business Impact, Operations, Risk & Governance, Innovation and Partnerships. Other executive views are not yet included. Registration is currently open; enterprise registration approval and the role-permission matrix remain decisions for deployment owners. New accounts have the `executive` role and an empty permissions list; no authorization grants are inferred.

## Local development

1. Copy `backend/.env.example` to `backend/.env` and `frontend/.env.example` to `frontend/.env`. The sample credentials are **development-only**. Supply a strong unique `JWT_SECRET` and database credentials in real deployments. Never commit `.env` files.
2. Start PostgreSQL 16: `docker compose up -d db`. Compose creates the development database. For a separately managed PostgreSQL server, create `DB_NAME` first and set `DATABASE_URL` and `DB_NAME` in `backend/.env`; the application does not create databases or require database-creation privileges.
3. In `backend`, create a Python 3.12 virtual environment, install `pip install -r requirements.txt`, run `alembic upgrade head`, then `uvicorn app.main:app --reload`. The API docs are at `http://localhost:8000/docs`.
4. In `frontend`, run `npm ci` and `npm run dev`; open `http://localhost:5173`. Vite proxies `/api` to the backend. Alternatively run `docker compose up --build` and visit `http://localhost:8080`; nginx proxies `/api` to the backend. Database data persists in a named volume. Existing volumes retain their original credentials and database name.

## Verification

Create a **separate disposable PostgreSQL database** named e.g. `canon_cio_test` with the same dev account. Set `TEST_DATABASE_URL=postgresql+psycopg://canon:canon-dev-only@localhost:5432/canon_cio_test` in the environment before running `cd backend && PYTHONPATH=. $HOME/venvs/app/bin/python -m pytest -q tests/test_auth.py` (or use your virtualenv's Python). Database-backed tests create, migrate and drop a fresh schema per test; the database user needs schema creation privileges. Never use a valuable database. Tests refuse a URL without `test` in the database name or one equal to the configured application database.

Run frontend component tests with `cd frontend && npm test`, production build with `npm run build`. For E2E, run the migrated backend and PostgreSQL, install Chromium with `node node_modules/@playwright/test/cli.js install chromium`, then `npm run e2e` in `frontend`. The E2E spec starts Vite and creates a unique real user in the configured development DB.

The strategic tests run with `TEST_DATABASE_URL=... PYTHONPATH=. $HOME/venvs/app/bin/python -m pytest -q tests/test_strategic.py` from `backend`. They use a fresh migrated schema per test in the dedicated disposable test database. Do not point them at valuable data.

## Strategic data and exports

Run `alembic upgrade head` before serving the strategic API. No business data is seeded. An authorized data owner must load verified observations into `strategic_metrics`: category (`business`, `risk`, `innovation`, `operations`), metric_name, metric_value, recorded_date and optional unit, trend (`up`, `down`, `neutral`), change_pct and insight. A metric name/category/date combination is unique. Load monthly budget comparisons into `strategic_budgets` with name, month (first day of month), optional unit, budget and actual; name/month is unique. Source systems, ingestion, KPI definitions and anomaly thresholds remain to be agreed. Stored insight text is displayed as supplied, not generated or assessed by the application.

`GET /api/v1/dashboard/strategic-metrics` requires the existing bearer session and returns latest observations for each category/name within the current and preceding eleven calendar months, all observations in that window, monthly comparisons, and the latest observations with nonempty insights. The reporting window ends on the current UTC date; missing months stay missing and future records are excluded. `GET /api/v1/dashboard/strategic-metrics/export?format=json` returns the same data, and `format=csv` returns dated observations and budget comparisons including insight text. Text cells beginning like spreadsheet formulas are prefixed with an apostrophe in CSV; JSON retains original text. The dashboard displays an empty state until data is supplied.

## Regional data

Apply migrations with `alembic upgrade head`. No regional records are seeded. A data owner must load one current row per region into `regional_performance`, including `region`, `health_score`, `availability_pct`, `security_score`, `transformation_index`, and status (`Excellent`, `Good`, `Warning`, or `Critical`). Availability must be between 0 and 100. Set `updated_at` when importing updates; ORM updates set it automatically. The application does not calculate severity, score definitions, causes, or global totals. Both authenticated `/api/v1/metrics/regional-radar` and `/api/v1/metrics/regional-performance` return `{ "regions": [...] }` with the same source values and timestamps; missing records yield an empty array. The radar plots raw values together without asserting that their scales are comparable. Investigation exposes the stored evidence for Warning and Critical rows, not inferred causes or actions.

Run regional backend tests with `TEST_DATABASE_URL=... PYTHONPATH=. $HOME/venvs/app/bin/python -m pytest -q tests/test_regional.py` in `backend`. They use a fresh migrated schema per test in the disposable test database; never use valuable data. The regional browser journey requires a separate disposable running app database containing a source-provided Warning region, and creates a real test user.

## Business impact data

Apply `alembic upgrade head`; no business observations are seeded. An authorized data owner may load `business_quarters` with one row per year and quarter (1–4). Supply `investment_m`, `revenue_attribution_m`, `cost_avoidance_m`, `operational_cost_savings_m` in USD millions, and `transformation_roi_pct` in percentage points as independently verified values; each may be NULL when unavailable. Specify `updated_at` when importing updates. Definitions, fiscal-quarter conventions and ingestion remain stakeholder decisions. ROI is not calculated; cost avoidance and operational savings are not assumed to be identical. The cards show values from the newest stored quarter, even when a field is missing. The stacked chart is a comparison, not a meaningful combined total.

Authenticated `GET /api/v1/business/impact?limit=20` returns the latest periods in chronological order, with `total`; limit is bounded from 1 to 100. Missing data returns an empty array, missing fields remain null. Run business backend tests with `TEST_DATABASE_URL=... PYTHONPATH=. $HOME/venvs/app/bin/python -m pytest -q tests/test_business.py` in `backend`. Tests use a fresh migrated schema per test in a disposable test database; do not use valuable data. The business browser journey requires a separate disposable running app database containing a business quarter and creates a test user.

## Operations data

Apply `alembic upgrade head`. No incidents or history are seeded. An authorized data owner can load `operations_incidents` with unique incident number, severity P1–P4, title, status Open, Investigating or Resolved, optional nonnegative MTTR minutes and timezone-aware creation and resolution times. Resolved records require a resolution time not earlier than creation; active records must not have one. `operations_history` stores one source-supplied reporting day per `recorded_date`: optional MTTR minutes, SLA compliance and uptime percentages, incident volume, resolution count, P1 volume and P2 volume. Counts are nonnegative and percentages are 0–100. Update `updated_at` when importing. Definitions, coverage, calculation windows, data completeness and ingestion are data-owner decisions; no SLA, uptime, MTTR or history is calculated from incidents. Resolution count is reported as resolutions per reporting day, not an inferred rate over another time window.

Authenticated `GET /api/v1/operations/incidents?limit=20&offset=0` returns the newest incident page and total; `limit` is 1–100 and `offset` is nonnegative. `GET /api/v1/operations/summary?limit=30` returns the newest supplied history in chronological order (maximum 100), its total, latest observation, and counts of stored Open or Investigating P1/P2/P3 incidents. Counts are null when there are no incident records; zero otherwise means no matching stored active incidents, not proof that ingestion is complete. A missing latest field remains null, not the previous value or zero. History is shown as supplied, without interpolating missing dates. The chart compares per-day incident volume, P1/P2 volume and resolution counts on separate axes.

Run operations backend tests with `TEST_DATABASE_URL=... PYTHONPATH=. $HOME/venvs/app/bin/python -m pytest -q tests/test_operations.py` in `backend`. They use a fresh migrated schema per test in a disposable PostgreSQL test database; never use valuable data. The operations browser journey requires a separate disposable running application database with at least one incident and one history row and creates a real test user.

## Risk and innovation data

The latter two are source-provided text; their scales and definitions are not inferred. The authenticated `GET /api/v1/governance/innovation` returns the latest outcome quarter and all supplied categories from the latest portfolio quarter independently; their periods may differ. Missing categories are not assumed to be zero. Amounts are not combined across units. Data ownership, ingestion, measurement definitions and completeness remain decisions for stakeholders.

## Partnerships data

Apply `alembic upgrade head`; no partner data is seeded. An authorized data owner loads `partner_performance`: unique vendor name, SLA compliance percentage (0–100), ROI multiple, source-defined delivery score, nonnegative annual spend, currency/unit, contract status, review quarter and optional innovation output. Annual spend and the current ROI are source-reported, not calculated. Load `partner_quarters` with partner ID, year, quarter (1–4), currency/unit, and optional spend, verified savings and ROI multiple. One row per partner and quarter is allowed. Update `updated_at` when importing changes. The data owner must establish score scales, currencies, fiscal-quarter conventions, verification and completeness; values from different currencies are not combined. Empty fields remain null. Quarterly ROI is not inferred from spend or savings.

Authenticated `GET /api/v1/partnerships?limit=20&offset=0&history_limit=20` returns a page of partners and their newest history in chronological order, with total counts. Limits are 1–100 and offset is nonnegative. The dashboard shows a chronological comparison table and allows supplier pagination; older history beyond the displayed limit is indicated. Run `TEST_DATABASE_URL=... PYTHONPATH=. $HOME/venvs/app/bin/python -m pytest -q tests/test_partnerships.py` from `backend`: tests use a fresh migrated schema per test in a disposable test database; do not use valuable data. ## Executive assistant

The authenticated assistant offers tab-specific starter questions (not AI-generated recommendations) at `GET /api/v1/ai/recommendations?context_tab=strategic` and accepts `POST /api/v1/ai/chat` with `query` (1–1000 characters) and `context_tab` (strategic, executive-summary, business, operations, governance, innovation, partnerships). The drawer and partnership-summary action send requests to these endpoints. Responses carry `source: "provider"` or `source: "mock"`. In provider mode narrative, actions and optional confidence come from the provider, not application calculations; confidence is not independently calibrated. Review output against source data.

For local development only, set `AI_MOCK_ENABLED=true` in backend runtime configuration and restart the backend. It defaults to false and takes precedence over `AI_ENABLED` when both are true. Mock mode returns fixed, explicitly labeled synthetic narrative, action and confidence examples; it does not analyze questions or dashboard records, contact an external provider, or provide decision support. Dashboard data and user sessions continue to use PostgreSQL; mock mode does not seed or replace dashboard data. Disable the flag for real provider mode or unconfigured-provider behavior. Never use mock output for decisions or enable it unintentionally in deployment.

No provider is enabled by default: chat returns 503 until deployment owners approve the provider, model, data sharing and security arrangements and set `AI_ENABLED=true`, `AI_ENDPOINT` (HTTPS OpenAI-compatible chat completions URL), `AI_MODEL` and `AI_API_KEY` in backend runtime configuration. Do not use the sample placeholders. The provider must support JSON-object response format and return JSON containing `narrative`, `actions` and optional `confidence`. Provider errors and invalid output return 502 without upstream details. Calls have a 15-second network timeout, a 64 KiB response limit, no redirects and no environment proxy; check provider retention, network policy and logging before enabling. Provider compatibility and real confidence require stakeholder validation.

Only up to 10 recent records from the chosen tab are sent, with selected numeric/status fields and dates; names, IDs, free text, incident titles and user/session records are omitted. Partnership context is anonymous, includes at most four recent quarters per record and excludes currencies and contract details, so it cannot reliably identify individual suppliers or compare monetary values across currencies. No context is sent until a chat request. Questions are sent verbatim: users must not enter PII or credentials. A basic credential-pattern check cannot detect all secrets; deploy appropriate data-loss prevention and access policy before enabling. Provider keys are used only in the outbound authorization header and never included in prompts or application logs. Missing data and sampling limitations are disclosed. These measures do not establish that a provider is approved.

Run `TEST_DATABASE_URL=... PYTHONPATH=. $HOME/venvs/app/bin/python -m pytest -q tests/test_ai.py` from `backend`; tests migrate and drop a fresh schema per test in the disposable database. Never use valuable data or run these tests against the application database. The browser spec requires real user creation and separate running deployments: an approved live provider with `AI_MOCK_ENABLED=false`, an unconfigured provider with both flags false (`E2E_AI_UNAVAILABLE_BASE_URL`), and a mock deployment with `AI_MOCK_ENABLED=true` (`E2E_AI_MOCK_BASE_URL`). The mock journey verifies synthetic mode only, not a live provider. Each frontend must proxy to its own correctly configured backend and disposable PostgreSQL database.

## API and security

`POST /api/v1/auth/register` accepts `username`, `email`, `password` and returns a profile (201); duplicates are 409 and invalid fields 422. `POST /api/v1/auth/login` accepts username/password and returns `access_token`, `token_type`, and `user`; bad credentials are 401. `GET /api/v1/auth/me` and `POST /api/v1/auth/logout` require `Authorization: Bearer <token>`; logout returns 204 and revokes only that session. Session records are checked on every protected request, along with user status, JWT signature and expiration. Passwords use bcrypt cost 12; passwords over 72 UTF-8 bytes are rejected. A token is held in sessionStorage, not passwords; refresh verifies it with the backend, and closing the tab clears it. Because script-readable tokens are vulnerable to XSS, deploy a restrictive CSP and consider a secure HttpOnly-cookie design before production.

Use TLS at the ingress and for remote PostgreSQL connections, secure secrets management, least-privilege database credentials, appropriate registration controls, rate limits, audit logging and an agreed role-permission policy before production. Dev Compose is HTTP-only and its default credentials and JWT secret are not safe for deployment. `GET /api/health` reports process liveness only, not database readiness.
